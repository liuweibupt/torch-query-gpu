GPU 数据库引擎并不好写：当前简单版还缺什么？

一个真正可用的 GPU 数据库引擎不只是“把几个算子放到 CUDA 上”。它同时需要 SQL 前端、关系优化器、GPU 算子库、显存生命周期管理、数据移动调度、压缩执行、错误语义、benchmark 和工程生态。本报告评估当前项目的简化 TQP/PyTorch 版本距离完整引擎还差哪些关键能力。

1. 总体判断

是的，一个 GPU 数据库引擎很难写。当前仓库已经打通了“SQL → DuckDB/Sirius-like frontend → TQPOperatorGraph → PyTorch/CUDA”的研究型链路，但它更接近可验证原型，而不是成熟 GPU DBMS。

当前已经有价值：项目证明了可以不手写完整 CUDA SQL engine，而是复用 DuckDB 前端和 PyTorch CUDA tensor operators，把 TPC-H 查询导入一个可执行的 TQP-style 路径。
当前主要短板：很多能力仍是“能跑”优先：通用 SQL lowering、物理算子选择、fusion、显存规划、压缩列常驻、复杂 SQL 语义、性能可解释性都还没有达到数据库引擎级别。

因此，这个项目下一阶段不应该只继续堆 TPC-H case，而应把每个 TPC-H pattern 抽象成通用 graph node 和 tensor primitive，逐步形成可组合的 compiler/executor。

2. 为什么 GPU 数据库引擎不好写

SQL 前端很复杂

SQL 不是简单表达式。真实查询涉及 name binding、type coercion、null semantics、subquery、CTE、window、set operations、correlated predicates 和权限/catalog。

优化器决定成败

GPU 上 join order、聚合策略、排序/TopK、pipeline breaker 和数据驻留成本常常比单个 kernel 更重要。

GPU 算子不是 DB 算子

PyTorch/cuDF/Triton 提供 primitives，但 SQL 需要 decimal、string、date、null、collation、stable ordering 和精确聚合语义。

显存是硬约束

HBM 容量小于主存。中间结果 materialization、hash table、sort buffer、group state 会导致峰值显存爆炸。

数据移动昂贵

CPU↔GPU、GPU↔GPU、NVLink/PCIe/InfiniBand、host spill 和文件 IO 都可能吞掉算子加速收益。

性能验证困难

需要区分 cold/hot、compile/data load/H2D/kernel/D2H/materialize，并用 Nsight/PyTorch profiler 解释瓶颈。

3. 当前项目现状

当前仓库的核心路线是复用成熟前端和 tensor backend，而不是自己从 CUDA kernel、SQL parser、optimizer 全部重写。

SQLSQL 文件或字符串输入。
DuckDB 前端parser、binder、physical plan 导出。
TQPOperatorGraph把 DuckDB JSON plan lowering 成图。
PyTorch backendphysical interpreter、graph nodes、少量 fused primitive。
CUDA ops复用 torch 内置 CUDA 算子执行。
SQL
  → DuckDB JSON physical plan
  → lower_duckdb_json_to_operator_graph(...)
  → PyTorchGraphExecutor / physical interpreter
  → torch.where / argsort / searchsorted / bincount / topk / gather / scatter-like ops
  → rows + DuckDB baseline validation
关键定位：当前项目不是 RAPIDS/cuDF SQL engine，也没有使用 RMM 管理显存；它是一个 TQP-style SQL-to-tensor execution 原型，主要复用 PyTorch 已有 CUDA 算子。

5. 显存与数据移动：目前最容易低估的部分

GPU 数据库引擎的瓶颈经常不是某个单独 kernel，而是中间结果和数据移动。当前版本依赖 PyTorch caching allocator，这能避免裸 `cudaMalloc` 的一部分开销，但它不知道 SQL plan 的全局生命周期。

风险：如果继续只优化单算子，而不做 query-level memory plan，那么复杂 join、sort、group-by 可能在 SF 更大或并发查询下因为中间 tensor、hash table、sort buffer 导致显存峰值失控。

建议补齐的内存能力

  • 为每个 physical operator 记录输入列、输出列、中间 tensor、估计 cardinality 和估计 bytes。
  • 执行前做 peak memory 估算：识别 pipeline breaker，例如 sort、hash join build、group-by。
  • 增加 tensor lifetime analysis：最后一次使用后释放或复用 buffer。
  • 区分 resident table tensors、query intermediate tensors 和 result materialization tensors。
  • 为 benchmark 输出 H2D、D2H、kernel、materialize、validation 分段时间。
  • 未来再评估 RMM/cuDF interop，而不是过早把 RMM 当作完整解法。

6. 算子与编译：下一步应从“能跑”转为“可组合”

当前 TPC-H 全部能跑是重要里程碑，但真正的目标应是：TPC-H 只是验证集，每个查询都由通用 lowering 自动生成 operator graph，然后调用可组合 tensor primitives。

类别 短期应该做成的通用节点 性能方向
Scan / Filter / Project typed column scan、mask expression、computed columns、null mask propagation。 融合 scan-filter-project，减少 mask/gather 中间 tensor。
Aggregate grouped/ungrouped sum/count/min/max/avg、HAVING、CASE aggregate。 dense group id、sorted group fast path、bincount/index_add fusion。
Join inner/left/semi/anti、multi-key、range predicate、subquery decorrelation。 sorted join、hash/index table、membership probe、build-side residency。
Order / TopK / Limit multi-key ordering、stable tie handling、offset/limit。 TopK pushdown，避免全量排序。
Compressed RLE/Index/Dictionary metadata、encoded predicates、late materialization。 在压缩域做 filter/aggregate/join，避免展开 rows。

7. 建议提升路线

P0-A

把 TPC-H patterns 全部拆成通用 graph nodes

目标是去掉 query-id/template 思维：每个 TPC-H 查询都只是 DuckDB physical plan 的一个实例，最终由通用 operator graph 自动执行。

P0-B

建立 operator contract 和 typed column model

统一 tensor、null mask、dictionary/string/date/decimal 表达方式，避免每个算子单独处理边界条件。

P0-C

做 query-level memory accounting

先不需要完整 RMM，但需要可解释的显存账本：每个节点分配多少、释放多少、峰值在哪里。

P1-A

扩大 fusion 范围

从 Q1 的 fused primitive 扩展到 scan-filter-project、group-by、TopK、semi/anti join probe 等高频路径。

P1-B

引入系统化 profiling

每次性能优化都要输出 operator breakdown、GPU kernel 时间、H2D/D2H、materialization 和 allocator 统计。

P2

压缩执行与生态互操作

把 RLE/Index/Dictionary 从实验 primitive 推到 storage metadata；评估 Arrow/DLPack/cuDF/RMM interop 的真实收益和复杂度。

P3

多 GPU / 分布式 / 生产能力

只有在单机 compiler/executor 足够干净后，再考虑 shuffle、partition、NVLink/InfiniBand、fault handling 和并发查询调度。
